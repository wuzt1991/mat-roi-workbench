## 3. 范围、目标与排除项

本轮以维护性改善为目标，功能行为以用户已确认的主会话要求为准。

### 3.1 必须达到的结果

- 修改列表布局或文案时，不需要修改计算公式和数据库事务。
- 单个 SKU、整商品、整表统一的作用范围明确，读列表和执行修改不共用含糊目标。
- 页面显示的数据来自同一已提交会话，过期响应不能替换较新结果。
- 失败后保留有效输入；结果未知时先核对，不直接重复执行。
- 当前计算与历史版本计算通过明确入口调用。
- 每一阶段有单独变更范围、验收记录和可验证的回退方式。
- 删除已经被该阶段替代的旧逻辑，避免新旧入口长期共存。

### 3.2 首轮交付范围

首轮完成阶段 0、1、2：基线、完整操作样板、商品转表模块化。阶段 3、4 的后续范围按商品转表样板的效果及用户当前授权决定。

首轮允许为了建立接口进行最小范围的 app.js、file-jobs.js、file-service.cjs 和成品清单调整。不可借此重写账本、保存队列、安装器或整个样式系统。

## 4. 必须保留的业务约定

这些约定决定重构是否正确。界面外观相似不足以通过验收。

### 4.1 商品转表流程

导入 Excel → 同一步确认材质与统一厚度 → 确认导出。复杂情况进入手动调整。

- 文件拖入和点击选择都保留。
- 正常数据完成材质与厚度确认后可以直接导出，不再被迫经过额外选项页。
- 未识别或多材质歧义在同一步处理，支持统一指定，也支持按商品链接分别指定。
- 记住上次选择仅用于预选；必须经本次确认才应用。
- 用户确认的统一厚度覆盖对应范围内原表厚度及厚度冲突。
- 手动调整按商品显示，展开后显示 SKU；保留单 SKU 和整商品材质、厚度修改。
- 原版等待动画、取消入口、计时和动效偏好继续保留。

### 4.2 商品和规格身份

- 商品键继续采用平台、店铺、商品 ID 的组合，不按商品名称分组。
- 身份不完整时，沿用保守隔离规则，避免把不同商品合并。
- 商品 ID、SKU ID、商家编码等身份字段保持字符串及前导零，不转为数字。
- 相同名称、相同 SKU 或重复源行不构成自动去重的授权。
- 展示可以汇总分组，原始行、工作表和来源行号必须可追踪。
- 缺失平台或商品身份导致的其他问题仍按原有校验提示，不能因分组显示成功就允许导出。

### 4.3 操作范围与厚度优先规则

| 操作 | 目标范围 | 保留与覆盖约定 |
| --- | --- | --- |
| 搜索 | 整份文件中的匹配记录 | 只影响显示；不改变导出、整商品修改或分母 |
| 展开商品 | 明确 groupId 对应的规格 | 分页读取，不把全商品所有行一次搬进浏览器 |
| 修改单 SKU | 明确 rowId 对应的源记录 | 只应用用户提交的字段 |
| 统一修改商品材质 | groupId 对应的全部目标规格 | 明确显示数量；遵循厚度与材质绑定关系，不保留失效组合 |
| 统一修改商品厚度 | groupId 内适用的全部目标规格 | 多材质不能盲套一个厚度规则；先确认材质或按有效材质处理 |
| 整表统一厚度 | 本次明确确认的材质及对应范围 | 覆盖原厚度与旧人工厚度例外，按已批准交互说明执行 |
| 普通重算 | 当前已提交原始行与修改记录 | 保留人工决定；按当前有效规则重新计算 |
| 再次明确统一 | 本次明确指定的范围 | 可重置该范围旧例外；不等同于普通重算 |
| 撤销 | 现有有效最近操作 | 版本或规则已变时拒绝不安全撤销 |
| 导出 | 整份已校验会话 | 不从当前屏幕可见列表生成 |

不要使用简单的永久“SKU 覆盖永远高于商品覆盖”规则替代操作语义。用户后来明确执行的整商品统一，可能正是要覆盖先前的 SKU 例外；普通重算则不应覆盖它。

### 4.4 导出格式

输出保持 29 列及以下顺序：

序号、平台、店铺、平台商品名称、平台规格名称、品牌、商品标签、尺寸、面积、宽、长、重量、成本、广告费、成交金额、主条码、规格辅助码、平台商品ID、平台规格ID、平台售价、售卖状态、平台库存、规格类型、规格名称、货品编码、货品简称、货品名称、商家编码、规格简称。

- 主条码、规格辅助码保持空白，不生成。
- 零库存保留为零；空值不能统一替换为零。
- 原商品名称、原规格文字和身份字段不因重构被规范化覆盖。
- 保留模板和现有公式残留修复；不得重新引入 G62 等旧公式问题。
- 规则、会话或修改版本变化后，旧导出产物不能误当作当前结果。

### 4.5 销售、定价、经营记录和总账

- 销售导入默认按商品成交订单数统计；按成交件数估算是单独口径。
- 同尺寸不同图案加总，长宽互换按现有规则识别；缺失、多尺寸和重复计划尺寸仍需明确处理。
- 多来源时保留来源选择；排除项不进入分母，合计舍入到 100%；全零数据不能形成有效占比。
- 一键添加缺失尺寸仍随应用动作一起保存；取消不得留下半个规格。
- 手动售价保护、复用规则选择、冻结成本与历史记录语义保持。
- 总账只汇总有效记录；已更正、已作废和旧试算不重复计入。
- 汇总 ROI 使用总成交金额除以总广告消耗，不能平均每条 ROI。
- 已入账结果与冻结快照保持；更正、作废走既有操作，不直接改写历史。
- 旧账字段按历史版本验证，不能为满足新格式补写历史金额。

## 5. 目标模块边界

先分职责，再决定文件数量。下表是目标边界，不要求每格机械拆成一个文件。

| 模块 | 输入与输出 | 不承担的职责 |
| --- | --- | --- |
| 应用外壳 | 工作区上下文、导航、保存提示、功能挂载与卸载 | 商品批量规则、成本计算 |
| 商品界面 | 视图数据、输入草稿、展开状态；输出用户意图 | SQL、导出拼接、独立业务公式 |
| 商品操作控制器 | 明确的动作、目标、上下文；输出已提交结果或可恢复错误 | 直接生成整页 DOM、复制数据库事务 |
| 业务计算 | 原始记录、有效规则、人工决定；输出确定结果与问题 | DOM、网络、文件路径、数据库连接 |
| 会话查询 | 分组、行分页、计数、筛选、修订号 | 改写人工决定 |
| 会话修改 | 校验上下文、事务提交、回执、撤销、计数更新 | 读取页面 DOM 决定范围 |
| 文件任务 | 导入、重算、导出、进度、取消与完成 | 推断用户未确认的业务选择 |
| 兼容入口 | 旧版本读取、验证、迁移、历史计算 | 随新界面改动重算历史 |

### 5.1 建议的最小拆分

商品转表前端优先形成四类模块：

1. 控制器：接收动作、调用服务、处理会话和任务状态。
2. 界面渲染：导入与设置页、商品与 SKU 列表、编辑窗口。
3. 视图状态：搜索、分页、展开、草稿与焦点；按实际复杂度可先与控制器同文件。
4. 服务适配：复用 file-jobs.js 对接现有 API，不为每个按钮重新封装一套请求。

建议名称可采用 public/product-transfer/ 下的 controller.js、views.js、editor.js。文件名属于规划；先检查项目加载方式，再确定实际路径。不要为轻微重复增加十几个微型模块。

服务端保留 ImportSessionStore 的公开入口与事务协调职责，优先抽出只读查询和纯规则辅助函数。只有在测试覆盖完整后，才拆分修改处理内部逻辑。单次业务操作仍由一个连接上的同一个事务控制。

### 5.2 依赖规则

- 界面依赖操作接口和展示数据，不能向后端传递“当前 DOM 中有哪些行”作为整商品范围。
- 计算模块不导入 UI、SQL 或桌面运行时。
- 数据服务不依赖视图层；浏览器和后端共用计算函数时，由各自适配器调用。
- 保留现有保存队列作为工作区保存入口，避免功能模块各自保存整份工作区。
- 循环依赖、跨功能直接改写内部状态视为边界未完成。
- 新模块进入运行时白名单，源文件存在不等于成品能加载。

### 5.3 历史兼容处理

先在现有公共入口封装版本分派，再考虑物理移动文件。旧模型还承担初始化或当前路径复用时，先解除这些隐式依赖，不能直接搬进“仅迁移时加载”的目录。

历史计算按其 calculationVersion 或既有判定规则选择实现。当前计算与历史计算可共用经验证的基础函数，但不得借抽取函数改变历史口径。

## 6. 状态与提交协议

本节防止把大状态对象机械拆成多个仍然相互矛盾的小对象。

### 6.1 区分五类状态

| 状态类别 | 例子 | 权威来源 |
| --- | --- | --- |
| 已提交业务状态 | 原始行、人工修改、派生代次、规则指纹、修订号 | 服务端已提交会话 |
| 用户输入草稿 | 尚未保存的 SKU 修改、尚未确认的统一厚度 | 当前编辑上下文 |
| 工作流程 | 导入、材质厚度确认、结果查看、手动调整 | 控制器依据会话与用户动作推导 |
| 后台任务 | 运行、取消中、已完成、失败、结果待核对 | 服务端任务状态与持久化结果 |
| 展示状态 | 搜索词、商品页、SKU 页、展开商品、焦点 | UI；不改变业务操作范围 |

初期不新增状态机依赖。用明确状态值和转换函数替换重复、矛盾的布尔组合即可。

导出可用性必须以服务端对全表、规则和会话版本的检查为准。前端按钮启用只是提示，不能成为唯一保护。

### 6.2 修改命令的约束

继续使用当前已有字段表达 workspaceId、storageEpoch、sessionId、ownerToken、expectedSessionRevision、mutationId、groupId 或 rowIds、patch 和 action。字段位置以现有 API 为准，不为了统一命名而修改兼容协议。

每次提交必须明确：

- 在哪个工作区、哪一代恢复上下文、哪个会话执行。
- 基于哪一修订号操作，规则是否仍有效。
- 目标是整商品还是指定源行，两者不能由前端可见范围隐式替换。
- 哪些字段保持、清空或明确赋值。
- 成功时变更数量、最新修订号、计数和撤销信息来自哪里。
- 错误时输入、已提交结果和当前任务分别处于什么状态。

同一动作的重试复用原 mutationId 和原请求体；用户改变内容后生成新动作编号。不能用新编号无条件重试一个结果未知的写入。

### 6.3 提交与失败分类

| 时点 | 必须表现出的结果 |
| --- | --- |
| 提交前验证失败 | 数据未变，输入保留，指出需修正的内容 |
| 事务中某一行失败 | 所有目标行、统计、撤销记录和回执共同回滚 |
| 提交成功且响应收到 | 展示新修订号对应结果，不保留过期列表摘要 |
| 提交成功但响应丢失 | 先读取回执或当前状态核对，不能直接显示未保存并重复执行 |
| 请求返回 409 冲突 | 不静默覆盖；保留草稿并刷新或提示重新核对 |
| 取消发生在提交前 | 等待后台停止，确认旧结果仍有效 |
| 取消发生在提交后 | 明确结果已经提交；不能宣称撤销成功 |
| 切换工作区或销毁页面后响应到达 | 依据上下文和请求序号丢弃，不污染新页面 |

现有 applyReview 回执可复用。若其他修改路径无法可靠判断结果，先补齐隔离故障测试并查明机制；不得伪造“未提交”状态。若确需持久化结构变化，转入单独数据迁移评审。

实施核验：UI 每次重试都会新建 mutationId，且没有只读回执核对入口；undo 尚未持久化回执。首轮在既有 receipts 表上补充只读核对和撤销回执，不新增表或改变业务字段。异步任务沿既有 job 元数据登记操作标识，核对目标操作而不只看修订号增加。结果未知期间保留原命令，禁止不同请求体冒用或自动重新写入。

### 6.4 UI 更新与草稿

实施核验：destroy 当前只移除监听，未使请求代次失效；undo 完成分支未核对原会话。候选统一检查销毁状态、上下文代次和会话身份，列表与展开详情一起发布同一修订号结果；失败保留最后可用视图。视图渲染不调用初始化写状态或读取偏好，这些移到控制器状态转换。

- 搜索与分页属于只读刷新，错误后保留先前可用内容及重试入口。
- 保存期间锁定当前编辑动作，避免双击和关闭窗口丢失输入。
- 保存失败保留用户原输入，不能把默认值重新覆盖回表单。
- 关闭、切换页面、切换工作区、退出应用时，继续沿用既有未保存保护。
- 进度轮询只刷新进度和必要状态，避免重建整页和重启动画。
- 第一阶段仅保证当前已有的草稿恢复能力；不承诺新增全部未提交选项跨重启恢复。
- 局部更新后仍检查焦点、展开位置、滚动位置、屏幕阅读标签和禁用状态。

## 7. 基线、比较与证据

可靠基线由准确源码、依赖、数据样本、操作步骤和预期结果组成，而不是一个版本号。

### 7.1 基线登记

记录以下内容：

- 用户已确认的功能要求及尚未确认项。
- 基线源码提交或完整源码快照；未提交改动不能遗漏。
- 关键源文件、锁文件和应用成品的校验值。
- Node、Electron、操作系统、硬件与测试运行方式。
- 数据库结构版本、计算版本、导出格式版本及会话派生版本。
- 每个样本的来源、用途、输入校验值、操作步骤和独立预期。
- 已知缺陷。存在已知错误时，明确哪些差异属于单独修复。

基线建立后，每次候选使用新证据目录。禁止重用旧报告文件冒充本次结果。

### 7.2 比较规则

| 数据 | 比较方式 |
| --- | --- |
| 原始行、原始文件 | 内容及哈希一致；不因重构改变 |
| 历史账目与冻结快照 | 原有业务字段完整一致，不用新公式回填 |
| 身份、零值、空值 | 检查类型与值，不能一律数值化 |
| 金额与计算结果 | 按现有精度及舍入约定比较；不能为通过而扩大容差 |
| 派生表 | 按业务行与当前有效代次比较，不能因内部代次数变化误报丢数据 |
| 回执、时间戳、临时 token | 仅排除明确不影响业务且有说明的字段 |
| XLSX | 回读单元格值、类型、列顺序和必要模板属性；不要求 ZIP 字节天然相同 |
| 新旧界面 | 验证行为和数据，截图用于布局核对，不以像素一致替代可用性 |

### 7.3 独立算例

至少准备以下独立于被测实现的预期：

- 一个面积、重量、成本可以手算的小表。
- 同尺寸不同图案合并与百分比分配样本，预期合计 100%。
- 两条消耗不同的经营记录，证明总账 ROI 按汇总金额除以汇总消耗。
- 零库存、零广告消耗、空值和无效值分别处理的样本。
- 含旧年代缺少后增指标字段的历史账目，证明读取兼容与历史不可改写。

预期结果不能调用被测 calculate、derive 或导出函数生成。发现基线本身错误时，单列缺陷修复和预期变更，不能因追求新旧一致而保留已知错误。

可直接采用以下最小预期作为独立样本起点。它们用于核对明确的单项口径，不替代完整业务模型测试。

| 样本 | 人工给定输入 | 独立预期 |
| --- | --- | --- |
| 面积、重量、材料成本 | 宽 40 cm、长 60 cm；重量系数 0.9 kg/m²；材料单价 10 元/m² | 面积 0.24 m²，重量 0.216 kg，材料成本 2.40 元；不含运费、税费等其他项 |
| 同尺寸图案合并 | 图案 A 的 40×60 为 3 单；图案 B 的 60×40 为 2 单；50×80 为 5 单 | 两个尺寸各 5 单，总量 10 单，占比各 50%；商品件数列不参与默认订单口径 |
| 排除后的分母 | 在上一样本外增加一条明确排除的 90 单数据 | 纳入总量仍为 10 单；占比仍各 50%，不能以 100 单为分母 |
| 汇总 ROI | 记录 A：广告 100 元、成交 1000 元；记录 B：广告 900 元、成交 1800 元 | 总广告 1000 元、总成交 2800 元、汇总支付 ROI 2.8；不能平均成 6 |
| 百分比舍入 | 三个已纳入尺寸各 1 单 | 显示精度为百分之一时，各项只差 0.01 个百分点，合计恰为 100%；余数归属按基线明确的稳定顺序验证 |

零广告消耗时 ROI 的空值或提示语义以现有已批准约定为准，不能在本次结构重构中擅自改成 0 或无穷大。

## 8. 分阶段施工包

每阶段先完成一条完整可运行路径，再扩展场景。相邻阶段可以共享已建立的接口，但不能把所有模块拆完才第一次验证。

### 阶段 0：固定基线与施工边界

前提：主会话当前功能已完成到可验收状态；重构范围已有用户授权。

工作：

1. 核对最新用户要求，将主会话已经实现的商品分组等变更纳入基线。
2. 保存完整源码与依赖快照，登记成品和数据版本。
3. 用独立副本建立样本及结果基线。
4. 列出模块调用、事件、全局变量、CSS 依赖和旧版本兼容入口。
5. 运行现有基线检查，分清基线缺陷与后续重构引入的失败。
6. 在独立施工副本或隔离工作树进行后续工作；来源必须包含已接受的未提交改动。

交付：基线清单、需求约定、测试样本清单、已知缺陷、模块依赖表。

通过条件：可以在隔离环境复现基线行为；原项目正在进行的工作和真实数据不受影响。

### 阶段 1：验证一个完整操作样板

工作路径：打开商品转表 → 搜索一个商品 → 展开 SKU → 修改一条 → 保存 → 重新打开 → 导出回读。

工作：

1. 抽取该路径所需的界面、控制器与服务边界。
2. 继续调用原有识别计算和修改事务。
3. 加入失败保留输入、旧响应拒绝和响应丢失核对。
4. 检查同一行结果、其他行、分组统计和业务工作区。
5. 在隔离环境对比原实现与候选。
6. 验证新入口加载到了构建成品。

交付：一条完整链路、关键接口定义、成功与失败场景证据、回退记录。

通过条件：单条修改、重开和导出一致，失败不产生额外变更；业务模块不依赖 DOM；界面不直接写 SQL。

未通过时：仅调整这条链路，不继续拆其他功能。

### 阶段 2：完成商品转表模块化

范围：导入、材质厚度设置、分组列表、SKU 编辑、商品批量修改、撤销、导出与恢复。

工作：

1. 逐个接入已确定的操作约定，保持现有 UI 决策。
2. 将读查询与修改命令分开；商品分页与 SKU 分页独立。
3. 保留整表搜索、跨页整商品修改和明确范围提示。
4. 按操作定义处理人工例外、普通重算与再次统一。
5. 保留多工作表、表头歧义、失败导入、文件替换确认和真实拖放。
6. 完成取消、并发、切换工作区、规则变更与重启恢复验收。
7. 删除已替代的旧入口、事件监听和样式；尚需兼容的代码注明原因。
8. 校验成品载荷和真实窗口；达到授权交付阶段后再替换本机。

交付：完整商品转表模块、行为测试、故障测试、性能记录、旧实现清理表。

通过条件：第 9 节商品转表及共用生命周期项目通过，当前业务数据与导出格式保持；没有第二条并行写入路径。

### 阶段 3：治理应用外壳和其他功能

前提：阶段 2 证明边界有效，主会话授权继续扩大范围。

顺序：

1. 外壳：统一功能挂载与卸载，保留一个工作区保存队列，分离导航与功能操作。
2. 可复用规则：明确规则编辑、验证、预览和提交入口；保持手动售价保护。
3. 销售导入：分离读取、汇总、人工映射、暂存新增尺寸和应用占比。
4. 经营记录：分离试算输入与冻结入账，保持更正、作废机制。
5. 总账：共用经营记录的汇总口径，集中处理过滤、汇总和明细读取。
6. 兼容：将版本分派集中到明确入口；确认依赖后再移动旧实现。

每一步单独验证，不能把商品转表的会话存储模式强套到总账，也不能把所有功能塞进一个万能控制器。

通过条件：该功能展示、保存、导出和恢复结果一致；局部修改不扩散到无关功能。

### 阶段 4：清理、成品验证与维护交接

工作：

1. 依据调用与运行证据删除无用代码；清理与保留理由逐项记录。
2. 整理样式作用域，保留两种主题和已批准动效。
3. 确认新增模块、资源、许可证与运行时白名单一致。
4. 在授权范围内验证最终 Mac、Windows 成品及升级。
5. 进行备份恢复演练，核验回退读取最新数据。
6. 更新当前维护文档，将废弃要求归档，避免主清单同时描述互相矛盾的流程。
7. 归档旧应用展开副本，保留可验证的回退产物和数据备份。

通过条件：候选来源、成品哈希、验收报告和交付记录对应同一次构建；未完成平台不得标为通过。

### 9.4 性能和容量

现有脚本包含 500000 行成功、500001 行超限拒绝、深分页 P95 不超过 500 ms、单行修改与撤销不超过 500 ms，以及验证进程峰值 RSS 不超过 512 MiB 的断言。施工时核对实际脚本与运行平台，不把这些断言当作本次实测结果。

新增分组验收至少覆盖：

- 一个商品包含大量 SKU。
- 大量不同商品，每个仅少量 SKU。
- 大量同名但不同身份的商品。
- 搜索命中很少记录及命中大量记录。
- 全商品批量修改、失败回滚与撤销。

分组查询和展开首屏采用同样的基准记录方式；正常分页操作的建议目标为 P95 不超过 500 ms，需在阶段 0 固定硬件和数据分布。若原基线已不满足，记录独立性能问题，不声称重构已改善。

阶段 0 固定本机、Node 24 和同一合成生成器，覆盖单商品 50000 SKU、10000 商品各 5 SKU、同名不同身份的 10000 商品；记录稀疏／广泛搜索、首屏／深页／SKU 展开的 P95 与 RSS。原有 500000／500001 完整链路作为最终容量验证；基线与候选分别输出，不复用旧报告。

512 MiB 是既有验证进程的口径，不是整个 Electron 应用的总内存上限。必须确认 resourceUsage.maxRSS 在各运行平台的单位；分别记录渲染进程、文件任务和测试进程，避免错误比较。

## 11. 成品交付与回退

交付前先保全当前状态，再替换应用；用户正在操作时不得用旧快照覆盖其新修改。

### 11.1 候选切换前

1. 确认没有未保存编辑、打开的未提交表单和运行中的文件任务。
2. 正常退出程序，或使用已验证的数据库一致性备份方法。
3. 备份业务数据、必要会话文件和桌面配置，验证副本内容。
4. 在副本上执行完整性检查、打开、恢复和导出，证明备份可用。
5. 记录候选与旧应用的版本、载荷哈希和签名检查结果。
6. 验证旧应用能读取新候选产生的数据副本，明确程序回退范围。

数据库处于 WAL 模式时，不在活跃写入过程中只复制一个 sqlite 文件。停机后备份或使用 SQLite 一致性备份，必要时保全 WAL/SHM 和会话关联文件。

### 11.2 切换与回退规则

- 替换过程保留可恢复旧成品；启动后核对版本、数据目录和当前会话。
- 用户尚未产生新编辑，且数据未变时，可按验证过的程序回退路径恢复。
- 用户已经产生新编辑时，优先仅回退程序并继续读取最新数据；必须已证明兼容。
- 无法证明最新数据可被旧程序读取时，先保全当前状态并停止自动回退。
- 恢复施工前备份可能丢失之后编辑，不能当作普通回退默认执行。
- 不把“备份存在”等同于“可以无损回退”。
- 同一操作的结果不明确时，先核对数据库与回执，不能以重新安装替代数据判定。

### 11.3 历史应用归档

只保留 /Applications/地垫工作台.app 作为展开的正式入口。旧成品和构建副本先压缩、逐项校验、记录恢复路径，再移除展开副本，避免系统应用列表出现大量历史版本。

归档清理不得删除业务备份、未完成施工源码、验收证据或用户测试期间的新数据。完全相同的应用副本可校验后合并，不能只凭版本号判断相同。

## 12. 停止条件与风险处置

停止只针对相关步骤，不自动中止可以独立进行的检查或文档工作。

| 编号 | 停止条件 | 下一步 |
| --- | --- | --- |
| S01 | 当前源码仍在并发变化，无法确定基线 | 等主会话完成当前阶段并登记准确快照 |
| S02 | 测试实际访问用户正在使用的数据目录或 profile | 停止测试，修正隔离配置 |
| S03 | 发现历史账目、原始行或其他商品发生预期外变化 | 保全输入和差异，定位原因，不交付候选 |
| S04 | 提交是否成功无法确定 | 核对回执和持久化结果，不盲目重复写入 |

## 13. 完成定义与停止扩张标准

重构不是追求全项目看起来一样。达到以下标准后，商品转表首轮可以收尾，不必继续扩大工程。

### 13.1 商品转表样板完成

- 已批准功能全部保留，正常用户的导出步骤不增加。
- 商品、SKU、统一修改范围和结果都可检查。
- 核心计算与持久化保护没有复制成两套。
- 渲染函数不执行写入，纯规则不依赖界面，修改事务边界清楚。
- 关键正常与故障场景通过，原始数据、人工决定和导出结果有对应证据。
- 大表分组、搜索、批量与分页的实际指标达到登记目标或有明确未完成项。
- 新模块在实际成品中可用，旧入口已移除或兼容理由已记录。
- 旧成品、数据备份与回退限制明确。

### 13.2 检验维护性是否改善

用两类变更做静态影响分析或隔离演练：

1. 调整商品摘要显示字段或布局：主要改界面和视图测试，原则上不触及公式与事务。
2. 增加一种已有业务操作的验证规则：主要改规则或操作层及对应测试，不到多个页面各补一份判断。

出现少量直接调用适配是正常现象，不设虚假的“最多改三个文件”指标。若任何小修改仍需同步改外壳、列表、弹窗、SQL 和导出，应继续修正边界，而不是宣布模块化完成。

### 13.3 后续扩张判断

商品转表样板通过后，比较实际修改范围、缺陷定位难度、测试运行方式和维护成本。只有改善得到证据支持，才把相同原则推广到规则、销售和账本。

不以自评全项满分、代码行数降低、文件数量增加或测试数量增加作为继续投入理由。性能和实际维护收益必须实测，纸面方案不能证明。
