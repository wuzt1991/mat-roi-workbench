原助手回复没有完整恢复；本文是重新调查后的方案，不声称复原了原文。用户于本轮明确选择：“按这份约 27 万行的大表设计”。

目标：实际约 27 万行的工作表无需人工拆分即可进入处理；读取、复核、批量操作、导出过程中界面保持可操作。沿用主线现有界面，上传一个文件、集中复核、导出一个文件；内部自动分批，界面不增加拆表页、任务中心或重复批量入口。

本稿的范围是商品转表和销售文件处理的容量与稳定性，以及与主方案的融合。27 万条销售明细可汇总到现有计划 SKU；不等于允许创建 27 万个正式计划 SKU，也不扩大正式工作区 20 MiB 请求上限。完整备份继续使用其独立协议。

施工只在隔离副本进行。主线C07已确认材质、厚度、尺寸三个同级字段和两类批量覆盖语义，不借性能改造复活已删的识别方案界面。

## 1. 第一个问题：为什么卡死，是否需要拆表功能

### 1.1 核实结果与证据边界

正式代码中存在下列路径，足以解释卡顿风险；没有当时的崩溃记录，因此不能断言这些就是那一次事故的唯一原因。

| 路径 | 已核实事实 | 后果 |
|---|---|---|
| `public/app.js:204` → `product-transfer.js:145` | 主界面调用 ExcelJS 完整加载工作簿，再检查工作表行列数 | async/await 不会把解压和计算移离主线程，行数校验发生得太晚 |
| `product-transfer.js:196` | 每次人工复核 JSON 深复制结果并遍历全部行 | 改一行也为整表付费，大表越用越卡 |
| `product-transfer.js:267`、`app.js:187` | 渲染前重新建立商品分组；规格名用数组 includes 去重 | 同商品大量不同规格时近似平方增长；有分页不代表计算已经分页 |
| `product-transfer.js:302` | 生成完整工作簿，最后 writeBuffer | 读取修好后，导出仍可能耗尽内存 |
| `persistence.js:9`、`app.js:86` | 整份工作区复制、JSON 序列化及 localStorage 缓存 | 若把原始表和复核行塞入工作区，会连带拖慢普通保存 |
| 合并前旧合同 C09（本次已替换） | Worker加载整本；草稿整体放IndexedDB；5000行上限 | 能改善小表响应，不能直接推导出 27 万行能力 |

本地实际文件只读扫描结果：

| 文件 | 文件大小 | 解压内容 | 实际规模 |
|---|---:|---:|---|
| `outputs/20260913_wangdian_transfer/旺店通26.2月_转表.xlsx` | 35.07 MiB | 298.51 MiB | 第一表 271,750 个非空行；第二表 159,320 个非空行；共享字符串 XML 48.89 MiB |
| `outputs/20260913_wangdian_product_transfer/商品转表-旺店通26.2月.xlsx` | 11.18 MiB | 143.54 MiB | 74,330 条数据＋1 行表头，29 列；包含 8 个 Excel 错误类型单元格 |

第一份用于真实大文件读取与资源验证，不能仅凭文件名认定其表头满足正式商品导入要求；第二份用于现有 29 列结构验证，错误单元格必须进入复核，不能当成普通字符串无声通过。

旧 `large-import-prototype.js` 是 09-13 的定时器演示；其 268,432 条、50 万行、关闭后继续等文案不作为证据。

本轮前置本机 Node 探针：5000 行同商品不同规格，现有分组约 212ms；内存试验用 Set 去重约 6ms，两组结果一致。单行复核现有逻辑约 38ms。它们是模型局部测量，不是最终 Windows 输入时延。

### 1.2 决定

不增加用户手动拆表功能。使用自动分批、磁盘暂存、按页读取、流式导出。

原因：如果拆表器也先加载整本 Excel，仍会在拆分前卡住；让用户拆分还会增加同商品跨文件、漏行、重复导入、复核决定难复用等问题。内部分批只是资源管理方式，不成为业务边界，不改变 SKU 原始顺序与分组规则。

## 2. 第二个问题：推演更好的方案与施工卡点

### 2.1 方案比较与唯一选择

| 方式 | 能解决什么 | 对本目标的不足 | 决定 |
|---|---|---|---|
| 加大行数上限、分页 UI | 减少 DOM 数量 | 仍整本解压、整表对象化、整表导出 | 不采用 |
| 浏览器 Worker＋现有 ExcelJS | 计算与界面分离 | 解压内存、数据复制、浏览器草稿容量仍不受控 | 不作为大表引擎 |
| 浏览器流式 XML＋IndexedDB | 可避免整本对象化 | 需要重建分页事务、配额、持久化与桌面恢复；现有本地服务已经可用 | 本轮不选 |
| 本机独立进程＋流式解析＋会话 SQLite | 分离 CPU、限制内存、保存复核、分页查询及事务 | 需要新增局部文件接口、进程生命周期和包内依赖 | 选定 |
| 完整 Node ExcelJS streaming | 有现成 reader/writer | 默认缓存全部共享字符串；emit 模式会临时保存工作表；writer 不保留现有模板全部部件 | 不直接采用 |

选定小依赖组合：`yauzl 3.4.0` 负责选择性 ZIP 流读取，`sax 1.6.1` 负责 XML 事件解析，`yazl 3.3.1` 负责 ZIP 流输出；SQLite 沿用 Node 内置 `node:sqlite`。不是另造 ZIP 算法，也不引入 Python、云服务或整套新框架。施工锁定确切版本与生产依赖闭包，保存许可证。

已发现并处理的选型卡点：`yauzl 3.2.0` 在本轮 Node 26 环境中读取真实共享字符串 XML 时停在尾部，进程仍存活但无进度。上游 3.3.1 变更记录明确修复 destroy/async iteration；本轮改验 3.4.0。不得使用旧版测试结果冒称新方案已通过；最终 Electron 自带 Node 与 Windows 仍必须测试。

### 2.2 复杂度收口

- 同一文件处理入口用于小表和大表，避免 4999/5001 行进入不同业务识别算法。
- 一份纯行识别/派生函数，同时服务转表预览、重算和导出；存储和任务调度不决定材质、厚度或尺寸。
- 一个调度器管理读表、重算、导出、备份等重任务；每工作区同时只执行一个重任务。首版不做并行批次、持久任务队列、跨电脑继续、关闭应用后台运行。
- 索引和分页是 27 万行的必要能力。复核规则版本变化时允许线性全量重算，但在后台进行；不制造复杂的任意增量依赖引擎。
- 首版中断读取后从源文件重新扫描；已完整导入的会话保留人工决定。不会把压缩流字节偏移伪装成可直接断点续读。

## 3. 第三个问题：细致施工合同

### D01 · 唯一状态与进程边界

```text
现有页面（当前页＋少量未提交输入）
    → 本机 HTTP 文件接口（流式上传、状态、分页、命令）
    → FileJobBroker（唯一重任务准入、代次、取消、退出判断）
    → 独立 Node 子进程（XML/计算/SQLite/导出）
    → dataDir/import-sessions/<随机 sessionId>/
       source.xlsx、session.sqlite、受控的 .part/最终导出文件

正式工作区 → 仍是原 Store / SaveQueue / workspace revision
销售应用 → 只将汇总后的必要字段送回原候选校验与保存路径
```

文件会话库保存临时原始数据和人工决定，不保存第二份正式计划或账本，不进入每笔 frame。转表不写正式工作区。普通小表也走同一会话库，禁止同一复核数据同时在 SQLite 和 IndexedDB 各维护一个权威副本。

调度器是每个本机服务实例一个；工作区标识使用 C02 的 workspaceId，并记录 storageEpoch。子进程负责同步 SQLite 和 CPU 工作；Electron 主进程/HTTP 主线程只做小消息、流式转发和生命周期控制。子进程复用通用受限执行入口，不能传任意脚本、文件路径或 SQL。

开发 Node 使用 `child_process.fork`；Electron 使用打包后的同一入口及 `ELECTRON_RUN_AS_NODE=1`。代码从 app.asar 的已列入 manifest 的资源读取，可写文件只在 dataDir。S0 最先验证最终 Electron 的 fork、sqlite、流接口；若包禁用 RunAsNode 或 API 不支持，则该技术段停工并修订，不能临时启用 renderer nodeIntegration。

### D02 · 明确的初版预算

以下是实现/验收预算，不是已经实现的能力广告。基准环境为 Windows x64、8 GiB 内存、SSD；记录真实 CPU/系统/安装包版本。

| 项目 | 初版合同 |
|---|---|
| 商品/销售源文件 | ≤100 MiB 压缩文件；只支持 xlsx；不接受 xls/xlsb/加密文件冒充 xlsx |
| ZIP 容器 | ≤4096 项；声明及实际解压总计 ≤1 GiB；实际读取计数独立核对 |
| 所选工作表 | ≤500,000 条业务行，最多 200 列；行坐标不超过 Excel 上限；表头前最多 40 个物理行 |
| XML | 所选 sheet ≤896 MiB，共享字符串 ≤256 MiB；workbook/rels/styles 各 ≤8 MiB；仍同时受ZIP总预算约束 |
| 单元格 | 文本 ≤32,767 UTF-16 单位；类型/长度越界明确指出来源行，不截断 |
| 处理批次 | 至多1000行且序列化内容≤2MiB，任一先到即落盘；单行规范化相关字段也须≤2MiB，超限按来源行明确422且不截断；一次XML输入块≤64KiB |
| 页面 | 100 个 SKU 行＋必要组标题；响应≤2 MiB；极长原文在页面截显，完整值按需读取，不截断存储 |
| 磁盘 | 每会话全部文件含 WAL/.part ≤2 GiB；会话总计≤8 GiB；保留至少1 GiB剩余空间，逐批复查/处理 ENOSPC |
| 内存验收 | 相比空闲时，renderer 增量≤150 MiB；大表子进程 RSS 峰值目标≤512 MiB；另记录整应用峰值 |
| 时间验收 | 27万行导入进入复核≤5分钟；27万行导出≤5分钟；缓存页交互p95≤200ms，冷页p95≤500ms；取消反馈≤200ms，释放任务≤3秒 |

500,000 业务行是上限，27 万行实际文件是必须通过的样本；两者分开验收。所选 sheet 超限明确失败；无关 sheet 超业务行数不得误拒绝，但整个 ZIP 仍受安全预算。格式化的空行不计业务行，不能根据 dimension 预分配数组；最后实际扫描得到的行数才是权威值。

磁盘配额不足不静默删除未完成会话。沿用恢复/放弃入口列出旧草稿，由用户明确放弃；完整源文件和已提交复核默认保留。上传未完成的 .part 下次启动可清理；导出临时文件在会话关闭/替换时释放，下载中的文件不得提前删除。

### D03 · 流式上传、预检和工作表选择

1. 在当前页选文件后，建立新的候选 session，不清空旧会话。浏览器直接将 File 作为 HTTP body 发送，不先 `arrayBuffer()`、base64、JSON 包装。
2. 专用上传路由用 pipeline/backpressure 写 `.part`，同时计算 SHA-256。失败、超限、取消均不发布新会话；完整关闭并核对大小后重命名 source.xlsx。
3. 上传完整文件后随机访问 ZIP 目录，再按条目流式解压；这里的“流式”不是声称能在ZIP上传完成前正确解析全部关系。验证路径、重复项、压缩方式、加密标记和预算；不把 ZIP 展开到任意目录。用 workbook.xml 与 relationship 定位工作表，不能假定 sheet1.xml 或 rId1 就是所选表。yauzl默认不校验内容CRC，选中XML/共享字符串等实际读取项额外用Node的增量`zlib.crc32`核对条目CRC；大小一致不等于内容完整。
4. 共享字符串逐条进入会话 SQLite；只保留有界缓存。读取前40个物理行的表头候选，多个合法表头由用户选择，不默认拼接所有 sheet。
5. 只有选定表才扫描业务数据。表头分值只用于候选排序，关键字段缺失/重复别名/多数量列由既有映射复核解决，不挑第一个错误表静默导入。
6. 完整验证新数据会话后，用户明确选用才替换当前会话。失败后旧复核仍在。

保留请求 Host/Origin/Sec-Fetch-Site 和 x-workbench 校验；文件端点仍仅本机。原 JSON body 上限20MiB不放宽，文件专用路由另算100MiB；所有客户端参数都用服务端生成的 sessionId 查找文件，禁止接受任意系统路径。

### D04 · 单元格语义与原文

解析器只实现所需的 OOXML 表格子集，并以 fixture 明确边界：共享字符串、inline string、富文本拼接、空值、数字原始词法、布尔、错误、公式缓存。XML 使用严格解析、UTF-8 流式解码，拒绝 DTD/外部实体，不能跨输入块丢半个汉字。原文在页面用textContent或现有转义函数展示，不作为HTML执行。

每行保存 sourceHash、sheetId、原行号、原始相关字段、类型及词法值。行 ID 为会话内稳定整数/明确命名 ID；不是当前页下标、筛选排序序号，也不是商品 ID。商品组键按三个独立字段平台、店铺、完整商品ID组合，缺身份逐行隔离；不得以字符串简单拼接制造碰撞。

文本 ID 保留前导0；数值型长 ID 即使 XML 词法看起来完整，也标记 Excel 已可能损失精度，不宣称可恢复；科学计数法不能先 Number 再转成字符串。日期按工作簿1900/1904日期制和样式处理；销售日期没有可靠语义时须选择周期，不能把日期序列号误当销量。

公式从不执行。普通数据字段存在明确缓存值可按缓存读取并保留来源标记；无缓存、错误类型及必须精确的 ID 公式进入复核/拒绝应用。导出没有公式。OOXML `_xNNNN_` 文本转义、富文本/注音节点、非法控制字符、XML转义单独回归；不能用普通正则拼接吞掉原文。

### D05 · 会话库与读取性能

每 session 独立 SQLite：

- `meta`：schemaVersion、workspaceId、storageEpoch、sessionId、ownerToken、sourceHash、phase、revision、derivedGeneration、rulesFingerprint、目标计划指纹、错误及时间。
- `raw_rows`：rowId、sheetId、sourceRow、原文/类型、原始平台店铺商品/SKU ID；导入完成后不可变。
- `reviews`：每行材质、厚度、尺寸、其余合法更正；pending/value/blank 和 auto/manual 来源按主合同；行 revision。
- `derived_rows`：某 generation 的展示/导出必要字段、状态、groupId、原始未写厚度标记；不复制整份原始200列。
- `groups`：完整组合键、原始顺序、组总数与状态计数、混合材质/厚度状态；最多3个规格示例，不持有组全部规格名数组。`group_value_counts`按generation/group/字段/状态/值维护数量，单行变化加减计数，不能为了更新“混合材质”再次扫描27万行大组。
- `shared_strings`：本文件共享字符串；`operation_changes`：正在准备的批操作及一次撤销所需旧值；`receipts`：有限的 mutationId 回执。

必建索引：原始行顺序；(generation,状态,原始未写厚度,groupId,rowId)；(generation,groupId,rowId)；组键的三个独立列；商品/SKU身份组合；reviews.rowId。实际查询用 EXPLAIN QUERY PLAN 和27万行用例核验，禁止每次翻页全表 GROUP BY/JSON 反序列化。

分页按稳定 group 顺序＋原行号，游标包含 session revision、筛选与排序摘要。允许单个超大商品跨页，重复显示其组标题及全组数量，不能为“同商品不拆批”一次渲染27万行。修改行使其退出筛选时，保存成功后重取本页、夹紧页码并修正选中集合；迟到页面响应按 requestId 丢弃。

### D06 · 人工选择、批处理与原子性

前端仅持有当前页和未提交输入；本地编辑先明确标“待保存”，服务端事务成功才标已保留。保存失败保留输入，禁止用旧成本冒充新输入的结果。逐行命令带 mutationId、expectedSessionRevision；同一内容重试返回同回执，同ID异内容拒绝。有限回执过期后仍按expectedRevision拒绝旧请求，不把同mutationId当新操作重放；显式接管使原ownerToken立即失效。跨窗口修改冲突刷新复核，不使用后来的 revision 盲目覆盖。

纯函数入口固定为 `deriveTransferRow(raw, review, immutableRulesContext)`；小表旧入口可批量调用同一函数，但不得保留两套自动识别算法。单行修改只重算该行及受影响组计数；规则成本改变则重算受影响引用，身份/识别规则改变可执行全量后台重算。

批量作用域不靠当前 DOM 推断：

| 入口 | 固定范围 | 覆盖约定 |
|---|---|---|
| 行内选择 | 明确 rowId | 用户明确更改该字段 |
| 勾选后的综合批量 | 操作打开时选中的 rowId；首版仅当前页可见勾选，不增加跨页全选 | 默认仅补待确认；显式覆盖才改已确认auto/manual值及blank；keep永不改 |
| 同链接材质/厚度下拉 | 完整 groupId 对应全部 SKU，含隐藏及其他页 | 显式统一所选字段，覆盖已确认auto/manual/blank；尺寸保持；显示全组及未显示数 |

当前C07已确定：同链接下拉为group-unify，勾选批量为selected-batch，行内为row-edit。三者是不同action；组下拉显式统一全组所选字段，勾选默认只补pending，不能共用隐含overwrite默认值。混合/待核材质禁用组厚度；材质ID变化清旧厚度并人工确认，名称变化不清。候选材质→尺寸→厚度保护顺序、伪亚麻、独立blank和软删例外均按C07。

全组大操作先按固定 session/rules revision 分批生成 operation_changes；校验所有目标合法后，在发布事务内再次核对storageEpoch、session revision和rulesFingerprint，一致后发布全部变更、派生及组计数并增加revision；失配丢弃staging且保留输入。准备阶段可取消；未提交的staging不可见。发布前父Broker取得短暂准入并重读当前正式规则指纹，相关规则的Store提交暂缓至会话事务回执/回滚确认后再继续；准备阶段不锁规则。规则库和会话库不是同一SQLite，不能只在子进程比较旧快照就宣称跨库原子。提交阶段取消只记录请求并核对事务结果，不能已提交却提示未修改。无需一笔27万行事务一直等用户输入。

一组混合材质不能直接套同一个其他材质的厚度；先按业务规则预览兼容/跳过数，非法输入整体拒绝，keep/value/blank 的合法跳过不是异常丢行。材质改变导致旧厚度无效时清除对应引用并待核；尺寸各自保留。以人工选择处理伪亚麻，不让优化绕过强制复核。

撤销仅保存本次操作影响字段的旧值，留在磁盘；只允许本会话无后续数据/规则修改时撤销最近一次。恢复候选和撤销发布同样使用原子事务，不克隆整个会话到浏览器。引用的规则软删除继续按主合同处理，不自动切换默认值。

### D07 · 规则变化、筛选和导出一致性

规则指纹为全部相关依赖的稳定业务内容摘要，包含保留的软删除引用及成本内容、规则有效/删除状态和影响auto候选唯一性的集合，不使用会因普通广告费保存而变化的数据库总 revision。涉及尚未保存的新规则的复核/导出，先flush原SaveQueue并确认成功，再取得对应不可变规则快照；失败保留输入并禁止假称已按新规则保存。重命名保留稳定 ID；成本改变清失效派生值；人工值和明确 blank 不重新猜测。

重算写入新 derivedGeneration，旧完整 generation 保留可看但标过期，导出禁用。重算期间本会话编辑锁住，其他工作区功能可用；完成后核对 source/review/rules 摘要，单次切换 activeGeneration，避免前半表新成本后半表旧成本。重复改规则仅保留最新重算意图，无长队列。

“未写厚度”来自原文解析事实，不等于当前厚度为空；手动补齐后仍满足原文筛选。未知8mm、多候选3/5mm不混入“未写”。更多筛选只改变显示；收起不暗清条件；筛选后的0行不代表整表复核完成。导出就绪始终按全会话 pending/错误总数判断。

导出指纹包含 sessionId/sourceHash/sessionRevision/derivedGeneration/rulesFingerprint/templateHash/exportVersion。生成过程中相关规则改变则任务失效；文件下载请求时再次校验。下载已开始后不能撤回用户收到的字节，因此定义“开始发送响应”为交付点，之后修改不改变该已交付快照。

### D08 · 流式生成29列模板

只有固定的受控模板参与输出，不接受任意用户模板。读取其小体积 ZIP 部件，保留工作簿关系、样式、主题、列宽、打印配置及元数据。用流式 sheetData 替换整段原表数据，更新 dimension/autoFilter，保留规定的首行冻结；按模板行样式循环生成新行。其余 ZIP 部件按校验清单保持。

该方案调整主合同原先“继续调用ExcelJS逐尾行删除”的实现要求，保留其业务结果：无共享公式、无G62残留、恰好29列、正确行数和样式、ID文本。替换整个 sheetData 后旧公式子节点根本不进入新数据；不是从空工作簿只抄几项样式。旧 exporter 在对照回归通过前保留为兼容验收基准。

每次读取会话最多1000行，逐行生成 XML，交给 ZIP 输出流；用 backpressure 等待落盘，禁止 build 全表字符串或 writeBuffer。文本写 inlineStr，数字写数字，人工 blank 写真实空单元格/null，字符转义不注入公式。旧空字符串在新协议下统一为真正空单元格；对照测试显式说明这一预期差异，不假称所有值逐字节相同。ZIP中不创建随27万行无限增长的全局共享字符串表。

模板中的autoFilter可能含WPS扩展属性和子元素，并非自闭合节点；只改`ref`并保留其余内容，XML解析/写出时保持命名空间。样式对照采用结构深等而非JSON属性顺序比较，另验列宽、行高、冻结与过滤范围。探针的固定模板字符串操作不直接进入生产导出器。

输出先写随机 `.part`，流全部完成、ZIP和行数校验成功后重命名。下载用本机流式 attachment，浏览器不得 `fetch→blob()` 再复制整个文件。生成成功与用户确实存到目标磁盘分开：只能提示“文件已生成/开始下载”，不能冒称用户保存成功。失败和取消不留下可下载的半文件。

模板含 calcChain、tables、drawing 或新关系时不能盲复制本方案假定；模板 hash/版本变化必须扩充部件检查及 fixture，失败停止导出。现有模板经检查为单 sheet，无表格关系，共900个公式节点；原稿小样本探针结果见§5.1，正式实现仍须覆盖完整模板fixture。

### D09 · 生命周期、取消、关闭与恢复

会话状态：uploading → inspecting → awaiting-selection → importing → reviewing；其后可 deriving/applying/exporting，再回 reviewing。failed/interrupted/canceled 保留来源与已提交决定。ready 由全部行的状态计算，不另存会漂移的布尔值。

每个命令/响应包含 workspaceId/storageEpoch/sessionId/jobId/generation；旧代次消息不准改变新会话。取消先关闭输入流/中止计算，子进程3秒内不能退出则强制结束并核对SQLite提交回执；父进程马上响应取消请求，不等待XML读完。任务结束、错误、退出时都释放文件句柄与IPC监听。

进度依据真实字节、已扫描行、已提交行与当前阶段，250ms节流；解析共享字符串时也有字节进度，不伪造百分比。原固定30秒总超时改为：60秒没有任何真实进展判停滞、总体15分钟资源预算；超时保留草稿、报阶段和原因，避免合法27万行被旧超时误杀。最终性能目标仍是5分钟，不用15分钟兜底冒充达标。

应用关闭：未确认输入或重任务触发既有退出保护；正常退出先提交已排队小操作，再停止进程。重开时 interrupted 会话可恢复已落盘人工决定；读取未完成可从保留源文件重新扫描，导出未完成可重新生成。首版不承诺“关闭应用仍继续跑”。浏览器页关闭而本地服务仍在运行时任务可能继续，但不是应用退出承诺。

源读取未完成的 raw_rows 处于不可发布 generation，重试整段重建；完整复核会话不清空。每批 transaction 提交后才上报已保存；进程强杀、断电、WAL恢复以SQLite实际提交为准，不能看前端进度猜提交。

工作区整库恢复成功：先停止文件任务，再增加 storageEpoch，旧会话保留为“原工作区上下文”供导出/重新复核，不自动附加到恢复后的新数据。仅workspaceId不够，因为C02规定恢复不改变workspaceId。storageEpoch存入正式SQLite元信息，与成功restore同事务递增；响应丢失后同operationId重试不得重复递增。GET state/recovery status返回该值，不能在解析坏业务JSON后才取得它。新规则引用需重新验证，不能沿旧ID静默套用。

### D10 · 草稿保全与销售提交

原 C09 的表单 IndexedDB 与未保存工作区 SaveQueue继续保留；仅商品/销售整表复核改由本机会话库。IndexedDB只记sessionId、当前页定位和少量未提交输入；筛选按C07刷新/重开复位，不能复制全部rawRows。缓存失败时保留前端未提交输入并提示；已确认在SQLite提交的复核不受浏览器配额影响。

会话救援导出为标明“非正式工作区备份”的流式JSON/NDJSON，包含来源元信息和人工决定，不能由主线程 JSON.stringify 全表。源文件可原样下载。救援有独立优先级：若重任务占用进程，先按D09取消并核对已提交状态，再用只读流导出，不排在卡住任务之后等其自然完成；不引入第二个不受控的重任务进程。若会话库本身损坏，则提供原源文件及会话原件，不伪造已恢复的JSON。正式业务备份仍是原Excel协议，不混入临时商品大表。

销售文件可有27万条重复SKU明细，后台汇总后按 C08 做绑定、数量校验和最大余数分配。只应用到现有计划SKU；未知ID、混合店铺/平台、重叠周期仍复核，不自动创建海量SKU。汇总时非负整数、安全上限、BigInt中间值与全计划100%份额合同不变。

应用销售候选绑定workspaceId/storageEpoch/shopId/planId/itemsFingerprint。提交前在最新工作区上只改sales/share/必要绑定/source，保留期间新售价；经原clone→校验→一次SaveQueue保存。请求20MiB预算按完整请求信封字节计算，不只算state。保存失败/409保留候选，不把会话已保存说成正式数据库已保存。
