## 1. 正式版优先修复

### B01 · P1 · 数据已损坏时，合法备份也无法恢复

- 位置：`server/store.cjs:39–56`、`public/app.js:98`。
- 复现：隔离数据库先保存合法账目并创建恢复点，再使当前 JSON 中的利润与冻结快照不一致；恢复点本身校验通过，调用 `write(validBackup, revision, 'restore')` 仍返回 500。
- 原因：恢复事务先调用 `read()` 校验损坏的旧内容，在处理合法备份前已经失败。启动错误页仅提供重新读取和下载恢复点，没有可用的导入恢复入口。
- 修订：专用恢复路径独立校验输入，读取原始 revision 与原始 JSON，在事务内保留损坏原件后替换；失败回滚。启动失败也能进入这条恢复路径。物理 SQLite 损坏需另有离线备份恢复办法，不能声称 JSON 恢复接口解决所有磁盘损坏。
- 验收：当前内容校验失败时合法恢复可成功；非法备份、错误 revision 和写盘失败均不得覆盖原件。

### B02 · P1 · 重启会替换用户自己设置的 1.35 元固定运费

- 位置：`public/app.js:91`。
- 复现：创建“合同固定运费”1.35 元并选用；打开正式页面后被自动改成 `shipping-zto-regional`，测试规格运费变为 1.45 元，并已写入数据库。
- 原因：每次启动都用“类型固定且金额等于 1.35”判断旧规则，无法区分用户新建模板。
- 修订：仅在有证据的旧版本迁移中处理已知旧内置 ID，迁移一次。普通启动不按价格猜测来源、不补回被删除规则。
- 验收：用户自建 1.35 元模板连续重启、备份恢复后 ID 和金额不变。

### B03 · P1 · 删除正在使用的厚度后静默换成本，当前窗口还会导出失败

- 位置：`public/app.js:354`、`:461`；`public/domain.js:40`、`:69`；`server/store.cjs:47`、`:72`。
- 复现：硅藻泥 40×60、3mm，从材料编辑中删除 3mm。成本从 2.28 变为 2.232；页面显示“已保存到电脑”，服务端改用 2.7mm，但客户端仍保存不存在的旧规则 ID。立即导出完整 Excel 失败。
- 原因：删除引用实体后计算器默认回退；服务端迁移会修正引用，而保存响应只返回 revision，客户端继续保留无效状态。
- 修订：引用中的规则软删除、保留原成本；候选工作区整体校验后提交。日常保存不进行隐式迁移，前后端使用同一份规范状态，禁止 UI 一套、数据库一套。
- 验收：删除→继续改价→导出→刷新→再保存，引用与成本一致，历史不变。

### B04 · P1 · 更新材料价格后，商品转表仍导出旧成本

- 位置：`public/app.js:210`、`:221`；`public/product-transfer.js:302`。
- 复现：先导入硅藻泥 40×60，再把 3mm 成本从 9.5 元/㎡改成 100 元/㎡，回到商品转表直接导出。实际文件 M2 仍是 **2.28**，按当前规则应为 **24**。
- 原因：导入结果携带旧 `rules`；导出使用这份旧结果，规则库更新不使它失效。
- 修订：预览、复核、导出统一按当前规则版本派生；规则变化后重算成本和重量，保留人工确认的材质/尺寸及明确留空状态。点击导出时冻结一份当前结果，文件与预览一致。
- 验收：改成本、系数、厚度、材质名称后再导出并回读，不能出现“可导出”但金额过期。

### B05 · P1 · 明确写了未知厚度，仍套用默认规则并允许导出

- 位置：`public/product-transfer.js:119–139`。
- 复现：`硅藻泥地垫 / 40*60cm 8mm`，现有库没有硅藻泥 8mm，结果仍为 ready，重量 0.216kg、成本 2.352 元，异常列表为空。这里使用模块旧默认规则；工作区路径同样存在 fallback。
- 修订：区分“未写厚度”和“写了库中不存在/多候选厚度”；后者必须进入复核，不能改用另一厚度。包边变体也遵守厚度约束。按本轮需求，用户可明确保留材质或尺寸为空，清空依赖金额。
- 验收：未知 8mm、3mm/5mm 冲突、标题与规格冲突、无厚度标准规则分别有明确结果。

### B06 · P1 · 客户端可用 migration 保存绕过冻结账目保护

- 位置：`server/index.cjs:50`；`server/store.cjs:46–56`。
- 复现：同一份删除历史记录后的工作区，普通保存被 422 拒绝，带 `reason:'migration'` 保存则成功，记录数量变为 0。
- 影响：这是本机保存协议的完整性缺口；不据此声称存在远程攻击或已发生账目丢失。
- 修订：迁移只由服务端受控版本升级执行。相同 schema 的普通写入不能因客户端字符串跳过历史检查。首次初始化和显式备份替换单独处理。
- 验收：伪造 migration 修改/删除冻结账目拒绝；合法升级保持旧记录原文；升级后的普通保存仍检查历史。

### B07 · P1 · 当前开发清单使测试和发布入口失效，版本号也不一致

- 位置：`package.json:4`；`package-lock.json:3`；`.github/workflows/release.yml:27–37`。
- 复现：工作区 package 版本为 1.1.9，HEAD 与 lock 为 1.1.10；scripts、开发依赖缺失。`npm test` 与 `npm run check` 均因 Missing script 退出 1，而发布流水线调用的正是这些入口。
- 修订：S0 恢复经核对的开发清单，保留已有业务修改；版本以真实发布记录递增。CI 增加 tag、package、lock、运行 health、更新清单和产物版本一致性检查。
- 验收：干净目录 `npm ci`、两个 npm 检查入口及不发布的打包命令通过。不能拿本机已有 node_modules 或裸 node 通过代替。

## 4. 一项业务口径需单独确认

`domain.js:176` 把“退货回收比例”同时用于 **已发货仅退款** 与 **退货退款**。而界面说明为“退货能收回的货品成本”。数值试验：全部订单已发货仅退款、回收比例100%时，单件原材料成本1.224元被计为0元。

现有 `refund-calculation.test.js:39` 明确覆盖并接受这个公式，所以不能仅凭名称认定实现偏离原约定，也不能自动修改旧账算法。需要确认：仅退款且商品未退回时是否允许回收商品成本；若不允许，应只对退货退款应用回收比例，并以新的计算版本作用于新测算，冻结历史保持原口径。**本项是业务决策待核，不计入已确认代码缺陷，也不阻塞其他隔离修复。**

## 5. 值得做的优化，按收益排序

1. **统一状态与校验。** 将一次性迁移、日常校验、缺省种子分开；输入→候选→校验→提交→派生结果只有一条路径。它直接解决 B02/B03/B04/R01/R02，收益高于换框架。
2. **规则 ID 与依赖失效。** 转表、定价、SKU、尺寸方案统一稳定引用；规则改动只重新计算受影响的当前数据，历史继续读冻结副本。避免名称当 ID、金额当迁移标记和缓存未失效。
3. **减少大表重复查找和整页重绘。** `domain.js:171` 每行遍历 sizes；`app.js:250` 每次输入逐行 querySelector。合成1000行单次计算约5.6–10ms，5000行约80–87ms，仅模型已超过一帧。先建 Map 索引、按当前规则版本缓存派生结果，再分页更新可见单元格；维持现有UI。结果是本机 Node 探针，不等同于 Windows 输入时延。
4. **完善错误定位与草稿。** “文件处理失败”无法说明是引用失效还是 Excel 错误；用稳定错误码和相关材料/SKU/行号，保留用户已填内容。退出提示必须和实际缓存能力一致，磁盘与浏览器缓存都失败时不能保证“关闭后可恢复”。
5. **补连续操作回归。** 现有测试偏重纯函数与正常提交。优先加入删除→导出→刷新、改规则→转表导出、恢复失败→重试、多窗口冲突、重启前慢任务。旧备份用固定 fixture，不在测试中用新 writer 临时伪造“旧版”。
6. **控制源码与包体。** 正式依赖图排除 review/pricing/large-import/ui-refinement 试验页面；按功能逐步拆 app.js 的事件与提交职责，合并样式覆写前做截图回归。无需为本轮功能整体迁移前端框架。

UI 层：正式版保留现有布局和风格，优先落实用户确认的折叠、统一规则入口、删除重复按钮。截图显示移动端导航占首屏较多，可沿用原型折叠导航；这属于次级改进。两下拉现有修订在本轮定位、上下避让、滚动、Esc/Tab/方向键检查中通过，未发现新的阻断项。未据此宣称已完成屏幕阅读器或所有缩放比例验收。
