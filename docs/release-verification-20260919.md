# v1.2.0 发布验证记录

本记录区分本地源码验证、Windows 最终产物验证和公开更新通道。用户已授权发布；未经验证的候选不进入正式更新通道。

## 2026-09-19 补充修复

1. 真实 60 行文件复核发现平台商家编码丢失。新版映射遗漏旧版的平台编码别名，且源文件同时存在空白内部编码列。已恢复平台商品编码、平台商家编码优先，并补回编号、行号、商品规格名称、价格、销售状态别名。新增测试先复现失败，再通过 XLSX 导入及导出验证编码和前导零。
2. 合成 500000 行的完整关联查询在第 5000 页耗时约 19.68 秒。已改为覆盖索引选出页面行号，再读取 100 行完整数据；分组重算改成逐行遍历。相同测试库修复后第 1/2500/5000 页分别约 77/84/90 ms，分组重算 9.80 秒、该进程 RSS 峰值 83.92 MiB。跨代、交叉筛选、分页顺序及分组数量回归通过。
3. 复核、撤销和恢复路径现在等待文件子进程真正退出后再关闭 SQLite 或删除会话目录；规则变更会阻止旧复核、撤销和导出，并要求显式重算。销售汇总任务进行中时，候选读取和绑定写入也会被任务空闲闸门拒绝，避免读取半成品聚合结果。

## Windows 与发布

Windows candidate 工作流已补入旧 v1.1.10 安装、旧客户端检测/下载候选、生产 IPC 重启安装、工作区版本迁移及原文 checkpoint、安装后包内容核对、包内 G62 和 500000/500001 边界。测试使用一次性 runner 和合成数据。升级探针只改旧测试安装的外部更新源，候选二进制不修改。

本轮 candidate `35431109311` 已证明旧客户端发现并完整下载候选包（SHA-512 与 `latest.yml` 一致），但可见 NSIS 窗口在 GitHub runner 上未被探针捕获，旧安装仍为 1.1.10，后续步骤因此跳过。更新入口已改为静默 NSIS 安装并强制重启，探针移除对交互桌面 UI 的依赖；修复后的新 SHA 必须重新跑完整 candidate。

候选工作流通过不自动发布。正式 tag 的发布工作流必须找到相同源码 SHA 的成功候选；下载该候选附件，校验版本、文件名、字节数及 SHA-512；先上传 draft 的三个附件，确认完整后才设为 latest。发布不重新构建。

当前仍等待 Windows 扩展验证通过。真实大表的 Windows 性能、实际 GPU/DPR 和完整 L01–L20 矩阵仍需逐项记录，不能把本地测试或启动检查标记为这些场景全部通过。

- 上游 electron-builder #7921/#8536 记录相同崩溃；已合并 #9769 指出 `SHGetKnownFolderPath` 返回的路径缓冲区被固定长度读取越界。项目锁定的 26.0.12 模板仍含该读取；升级到 26.15.3 后核对模板已使用有界 `lstrcpynW`。不以换 runner 代替修复新版安装器。
- 旧基线升级验证固定 windows-2022；另一个 windows-latest job 必须使用同一候选附件，连续三次安装并启动验证。既有旧版安装器不重写。
- `35426862479` 已验证旧客户端检测和下载候选，重启观测超时，未标记成功。探针随后改为一次性 runner 的正式默认数据目录和端口，避免 NSIS 经 shell 重启丢失测试环境变量；自动重启先独立核实进程路径与数据，再单独启动 CDP 渲染诊断，不冒充自动重启证据。
